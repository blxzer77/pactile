# Parallel-first execution contract

> **Purpose**: Make “parallel by default, serial by written reason” a **product** principle and an executable planning contract. After a Task is Open, first judge isolatable units; if they exist, prefer **host-native** parallel. Pactile owns declaration + integration only.
>
> **Bounded batch, not a generic scheduler.** `pactile parallel run` dispatches approved Pi Child tasks from a Parent manifest. Codex desktop Execute tasks continue to use native App tools plus Pactile requests and receipts.
>
> **Scope:** Parent/Full fan-out, independent isolatable Tasks, and independent middleware / protocol / release tracks. **Not:** Lite / single-file (spawn not required); unisolatable write-sets; HITL / `start-execution --approved` / reviewer / `integrate-child`.
>
> **Strength:** convention + Independent Check / planning review. Missing declaration on Full/Parent is **Check FAIL**. Not a `start-execution --check` hard gate. Attention order (`priority`) is not a serial lock.

Full Prefer/Adapt/Own and serial-exception list: `.pactile/workflow.md` (Parallel-first). Host binding lives in the Adapter guide, not this contract. Who/where dispatch: `.pactile/framework/execution-strategy.md` (orthogonal).

---

## Open, then judge isolation

1. After Open, name isolatable **write-sets / deliverables** (different `touches`, different Child, independent slices). Role chains stay serial: implement → Check. Independent research slices in Define may run in parallel; research must not share an Execute write-set.
2. Point to **≥2** isolatable units → default parallel. Cannot point to more than one (true single write-set) → main session inline and write `serial_reason` (or one equivalent line). Full / Parent should normally be able to name units. Lite does not forbid fan-out; it usually has one write-set.
3. The main session is dispatcher + HITL + integration, not the default sole implementer.
4. Prefer a **host-visible parallel surface** when the Adapter can open one. If it cannot bind, record assurance and degrade to inline / sequential — do not claim work already ran in parallel. Same-session silent workers are a degrade and need one plain sentence.

## Declaration XOR (task-map / implement.md)

Planning must pick **exactly one side** (aliases allowed):

- `parallel_groups` (or existing alias `stages`) lists isolatable units, and unit `touches` do not overlap (or isolation such as `git-worktree` is declared); **or**
- `serial_reason` is one of: shared write-set / HITL or reviewer gate / `depends_on` unmet / user asked serial / conflict surface cannot isolate.

Declare these in Parent `task-map.md` (frontmatter and/or Orchestration notes). For a Full task with explicit worker fan-out and no Parent, put the same block in `implement.md`.

| Need | Field | Where it already lives | Notes |
| --- | --- | --- | --- |
| Topology | `execution_topology` | task-map frontmatter | `parallel` (default when ≥2 independent units) or `serial` (requires `serial_reason`) |
| 可并行组 | `parallel_groups` *or* `stages[].units` | `stages:` already groups units | List child / slice ids that may run concurrently (empty `depends_on`) |
| 合并点 | `merge_points` *or* `merge_limit` | `merge_limit: 1` + `integrate-child` | HITL, `start-execution --approved`, reviewer gates, and Parent integrate stay **serial** |
| 冲突面 | `conflict_surface` *or* `children[].touches` | per-child `touches` | Write-sets that can collide; isolate with worktrees or serialize |
| 串行理由 | `serial_reason` | required when there are no isolatable groups | Exactly one of the exception list above |

`serial_reason` (one of):

- shared write-set
- HITL or reviewer gate
- `depends_on` unmet
- user asked serial
- conflict surface cannot isolate

Lite true single write-set: one line is enough (`serial_reason: single write-set`, or omit the parallel block and state inline in `implement.md`).

Optional YAML (Parent frontmatter or Full `implement.md`):

```yaml
execution_topology: parallel
parallel_groups: [child-a, child-b]
merge_points: [integrate-child, reviewer-gates]
conflict_surface: [path/that/collides]
# serial_reason:  # omit when parallel groups are declared
```

These fields remain planning declarations. A Parent can opt into an actual bounded batch with `pactile parallel run`; dispatch checks current approval, dependencies, declared write sets, review cost and the Parent cap before launch.

---

## Check FAIL (Full / Parent)

Independent Check / typed Check worker (helper: `common.parallel_declaration.evaluate_parallel_declaration`) is **unqualified** when any of:

1. Neither `parallel_groups` / `stages` nor `serial_reason` is declared.
2. Isolatable groups are declared, all write-set work stayed inline, and there is no `serial_reason`.
3. Two workers share a write-set and isolation was not declared (fake parallel).

Lite missing the block is not FAIL. Archives are not backfilled.

This is **not** a `pactile task start-execution --check` hard fail.

---

## Worker binding window

Activate `worker-orchestration` when — and only when — isolatable groups are already declared **and** a dispatch window is open (Execute-approved implement workers; independent research slices under Define). Parent may not silently finish children in sequence without a written `serial_reason`.

HITL, `start-execution --approved`, reviewer, and `integrate-child` (`merge_limit: 1`) stay serial. Human attention: batch questions on one frontier; do not multiply confirms by N. Run `pactile parallel status <parent>` to read wall time, queue wait, recorded rework events, Child outcomes, and current integration states.

## Non-goals

- Unapproved automatic dispatch or a persistent general-purpose queue
- Forcing Lite tasks into parallel agents
- Replacing the host-native parallel surface
- Relaxing HITL / `start-execution --approved` / reviewer-gate serial semantics
- Cross-platform parallel (P16)

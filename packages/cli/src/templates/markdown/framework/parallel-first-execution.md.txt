# Task/Run critical-path scheduling and safe concurrency

> **Compatibility filename:** this document remains at `parallel-first-execution.md` so existing installations can receive template updates. The filename does not require parallel dispatch or a particular execution mode.

This contract describes current Task Kernel V2 planning and Run execution. The scheduler is host-neutral; an available host integration is optional. A schedule is a plan and receipt, not permission to start a Run.

## Decide from the critical path

1. Validate the complete dependency graph before planning. A missing dependency or any cycle fails the whole planning call; no schedule plan or receipt is produced.
2. Before dispatch, each dependency must have a successful Task Close: its lifecycle is `closed` and its outcome is `completed`. A completed Run alone does not satisfy a dependency. An open dependency keeps its dependent Task undispatchable, even if a later advisory schedule wave lists it. A failed or blocked dependency blocks downstream Tasks; unaffected eligible Tasks may still be scheduled.
3. Apply local readiness and authorization rules before considering concurrency. A scheduler suggestion cannot make an unapproved, blocked, stale, or otherwise ineligible Run dispatchable.
4. Compare known Run write sets. Overlapping writers run sequentially by default. Concurrent overlap requires exact Task-pair authorization, approval evidence, a named integration owner, and an integration plan. Unknown write scope conflicts with every writer.
5. Require real isolation for concurrent writers. Separate agents, sessions, or host names do not prove isolation. A managed Run worktree must match the Kernel write-set snapshot and pass the manager's current workspace checks.
6. Estimate end-to-end completion time, including waiting, execution, rework, integration, and Review. Schedule compatible work together only when the modeled completion time improves over the serial plan. Missing estimates remain explicitly unmeasured in the receipt.

Pactile imposes no fixed numeric concurrency cap. The plan is limited by dependency readiness, authorization, write-set compatibility, isolation, current leases, and the completion-time comparison. A plan may therefore contain one task even when several tasks were requested.

## Optional host dispatch

The scheduler does not choose an execution authority, create a Run, acquire a writer lease, or start a host. A caller may dispatch an eligible Run through a supported host integration after the required Kernel admission checks. If no suitable host or safe workspace is available, keep the Run unstarted and report that state; do not treat a plan as execution evidence.

Immediately before dispatch, re-read the Kernel, dependency state, authorization, schedule receipt, worktree, and active leases. If any bound fact has changed, discard the stale plan and recompute. Host completion alone does not prove that the writer stopped or that the Run succeeded; retain the required host-stop and Run-result evidence.

## Review and Close remain separate

A completed Run is not a Review or a Close. Review the exact candidate recorded for the latest completed Run, and record an independent Review with its evidence. Close requires the latest Review for that candidate to pass, with no unresolved blockers and evidence for every acceptance criterion. Review cost contributes to the completion-time estimate; it does not impose a project-wide concurrency rule.

Keep estimated costs, measured dispatch time, and lifecycle-observed costs distinct and attach their evidence references. Do not infer missing time or cost values from task count, provider confidence, or a successful outcome.

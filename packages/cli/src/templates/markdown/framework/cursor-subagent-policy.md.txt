# Cursor Subagent Policy

> Current policy for dispatching Pactile research, implementation, and check
> work through Cursor's supported native agent surfaces.

This is the **Cursor binding** for the host-neutral `worker` slot. Codex binds
the same slot to cross-session dispatch instead — see
`codex-worker-dispatch.md`. That split is declared in `execution-strategy.md`
and is deliberate: Cursor has no cross-session surface, so subagents are the
native answer here.

## Invariants

- Pactile never hardcodes vendor model identifiers in committed defaults.
- The operator chooses the main-session model; a child inherits it unless the
  native host surface provides an explicit supported override.
- A child receives the smallest sufficient context pack and a concrete task.
- The Parent owns decomposition, integration, and final acceptance.
- A child does not recursively dispatch another Pactile child.
- Model choice is not evidence. Source reads, diffs, tests, and receipts are.

## What the host gives you, and what it does not

| Property | Reality on Cursor |
| --- | --- |
| Topology | A tree: `parentComposerId` / `childComposerId`, with a root at `rootParentConversationId` |
| Nesting | Host budget is 3 levels. Pactile is stricter: a Pactile child never dispatches another Pactile child, so in practice one level |
| Returning to a child | Possible (`resumeAgentId`), but Pactile dispatch stays one-shot per child |
| **Result flow** | **Results return only to the parent.** There is no sibling-to-sibling channel — children spawned together cannot see each other's output, and there is no shared inbox they can read |
| Wake-up | The child wakes the parent (`background-task` or `file-inbox`); it cannot wake a sibling |

**The result-flow constraint is the one that changes how you plan.** Two children
dispatched in parallel are not a team: they cannot coordinate, split emerging
work between them, or build on each other's findings. If a later unit needs an
earlier unit's output, either dispatch it after the earlier child's result
reaches the parent, or route the information through the parent explicitly.
Planning that assumes peer-to-peer children will produce children working from
stale assumptions.

## Which tools a child can use

A child's toolbox is the `tools:` list in its agent definition. Two rules apply:

- The list may only name MCP servers that Pactile itself declares for the
  project. A server the user configured is the user's to add; Pactile does not
  assume it, and a whitelist naming a server that no one has would silently cost
  the child a capability it was told it had.
- Anything named must survive being absent. A missing MCP server degrades that
  one lookup — exact search and direct reads still work, and the child should
  say what it could not check rather than stall.

The current definitions grant `mcp__codegraph__*` and `mcp__fast-context__*`
for repository work, and `WebSearch` / `WebFetch` to the research child for
external facts.

## Dispatch roles

| Role | Purpose | Workspace access | Expected output |
| --- | --- | --- | --- |
| `pactile-research` | Answer a bounded repository question | Read-only | Findings in the assigned research path |
| `pactile-implement` | Implement one frozen write set | Writable | Scoped changes plus focused verification |
| `pactile-check` | Independently verify requirements and safety | Read-only by default | Verdict, evidence, and actionable findings |

Use Cursor's built-in exploration surface for quick orientation that does not
need a durable artifact. Use a Pactile research child when the result must be
persisted, cited by a task, or kept separate from implementation context.

## When to dispatch

Dispatch only when the work is independently bounded and parallelism or
context isolation materially helps. Keep work inline when it is a single small
change, when every step touches the same write set, or when coordination would
cost more than execution.

Before dispatching:

1. Freeze the child objective and write set in the Parent task map.
2. Include `Selected task: <path>` as the first line of the child prompt.
3. State whether the child is read-only or writable.
4. State the required validation and stop conditions.
5. Confirm dependency readiness and worktree ownership.

## Model policy

`model_policy: cursor-configured`

Use only controls exposed by the current native Cursor surface. If no child
override is available, inherit the Parent model and record that fact. Never
edit generated agent files temporarily to smuggle a model identifier into a
dispatch, and never mutate user settings as part of task execution.

## Isolation and integration

- Parallel writable children require disjoint worktrees or explicitly disjoint
  write sets.
- A shared worktree implies serial writable execution.
- Research and check children may run concurrently when they are truly
  read-only and do not compete for mutable generated state.
- The Parent reviews each child diff before integration and re-runs the union
  verification after all accepted changes are present.
- Do not mark a check `true-independent` when it was performed by the same
  writable execution context or by a generic child standing in for a missing
  checker role.

## Failure handling

- Missing native child support: continue inline or open a separate user-owned
  Agent chat only when the task contract permits it.
- Busy or interrupted child: preserve its partial evidence, reclaim the lane,
  and retry only the unfinished unit.
- Write-set overlap: stop the conflicting child, reconcile ownership in the
  Parent task map, then resume serially.
- Unavailable model override: inherit the Parent model; do not block safe work.
- Unverifiable result: treat it as orientation and reproduce the proof in the
  Parent context.

## Closeout

The Parent records:

- which role ran and whether it had write access;
- the exact task/worktree and write-set boundary;
- accepted or rejected findings;
- focused validation from the child;
- union validation after integration;
- any degraded host capability or unresolved blocker.

Historical client-specific routing experiments are intentionally absent from
generated runtime guidance. They belong in versioned history, not in a fresh
Pactile installation.

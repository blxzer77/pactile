# Requirements and planning questions

Use this guide when unresolved decisions affect the Task deliverable, acceptance criteria, dependencies, scope or material risk. Deep planning and Grill are optional methods; Task size and question count do not create new gates.

## Read facts before asking

Inspect current code, constraints and applicable prior research first. Ask the user for intent, preferences, authorization and trade-offs that evidence cannot decide. Do not ask them to confirm repository facts or repeat an existing scoped grant.

Resolve only questions whose prerequisites are decided. Present up to three independent choices together, each with a recommendation and its trade-off; keep dependent decisions pending. Continue authorized independent work while awaiting an answer. Stop asking when further questions would not change acceptance or risk.

## Definition checklist

| Check | Evidence needed |
| --- | --- |
| Goal and value | One independently acceptable deliverable |
| Facts and assumptions | Current sources; uncertainty identified |
| Acceptance | Observable criteria that distinguish incompatible outcomes |
| Scope | Explicit non-goals and authorized write boundaries |
| Dependencies | Known Task IDs, successful-Close prerequisites and sequencing |
| Delivery | `local-result`, `pull-request`, `merged-result` or `documentation` |
| Reuse | Existing capabilities, permitted mature alternatives or justified self-build |
| Design risk | Interfaces, state, isolation, failure handling and rollback where relevant |
| Verification | Required gates plus checks for affected public behavior and material risk |
| Open decisions | Only unresolved choices that can change the result |

Use [reuse before building](./reuse-first-guide.md) and [risk-driven verification](./verification-strength-guide.md). Do not create a dependency tree, document bundle or exhaustive research exercise when a small definition already suffices.

## Artifacts and authority

The unified Task Kernel reader identifies the schema. For V2, the Kernel owns the definition, ACs, delivery level and hard dependencies. `prd.md` is authored explanation, not a state patch. Create a Task only after agreement to its proposal; implementation needs an authorized, admitted Run.

Agent-facing context uses `pactile task artifacts <task> --agent`, then fingerprint-bound facts/documents/sections. Human-facing Markdown explains the decision in the user's language. Put technical Decision/Rationale/Risk in Task `design.md`; use `implement.md` for ordered work, write boundaries and chosen checks when those details help. Do not fill redundant documents or synthesize a missing Kernel fact.

An approved narrative change cannot silently alter an executed definition. Use a supported authorized update path or coordinate a new Task/Run; do not invent an automatic Return-to-Define transition.

## Optional Grill

Check the existing definition and authored documents in the current conversation. Inspect unexplained assumptions, conflicting AC interpretations, unnecessary complexity and unresolved risks. This retains useful document-review practice without a mandatory new Subagent, a standalone slash command or a bundled `brainstorm` dependency.

Finish when the deliverable, ACs and boundaries are clear, blocking decisions are resolved, and required authorization is available. Proceed through the current [V2 workflow](../workflow.md); V1 `start-execution` applies only to a Task explicitly identified as legacy.

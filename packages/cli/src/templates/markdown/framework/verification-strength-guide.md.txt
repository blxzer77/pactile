# Risk-driven verification

Choose checks from the Task's acceptance criteria, changed public surfaces, material failure risks and repository-required gates. Task intensity, hierarchy, number of files and presence of planning documents do not determine verification strength.

## Select useful evidence

1. Identify the exact result being checked and every AC. For final V2 acceptance, use the latest completed Run's candidate ID/fingerprint and current candidate observation.
2. List affected behaviors and risks: data loss or migration, authorization and privacy, concurrency, lifecycle/compatibility, public interfaces, shared infrastructure and external integration where relevant.
3. Preserve required repository/CI checks and explicit AC requirements. A caller inventory or model recommendation cannot remove them or claim the complete CI inventory is known.
4. Reuse relevant existing checks first. Choose the smallest set that observes the changed public behavior and remaining risks. State what the evidence cannot prove.
5. Expand only for a concrete remaining risk, an unresolved failure or a required gate. Repeat a check after an affecting change, stale observation or plausible flaky/environment cause, not simply because an Agent can run it.

## When to write or run a test

| Situation | Useful choice |
| --- | --- |
| Reversible local prose or mechanical metadata edit | Inspect the changed content and actual references/projection; do not create a wording mirror |
| Changed public behavior or reproduced defect | Existing targeted test, or a regression that fails for the real defect at a public seam |
| Authorization, mutation or migration boundary | Success and refusal/preservation behavior with actual inputs and state |
| Race or shared-resource risk | Relevant interleaving/concurrency proof; sequential green tests alone may be insufficient |
| External host/provider dependency | Separate simulated contract proof from authorized real connection acceptance |
| Global/shared build or schema change | Broaden type, contract, package or regression checks as the affected surface requires |

A valuable test detects an observable wrong result. Assertions that restate internal implementation, count helpers, or mirror prose cannot replace behavior proof. Do not add one test per function or run the whole suite after every local edit. Full regression is appropriate when its additional coverage addresses shared risk or a required gate; repository CI may supply that evidence when its scope and SHA match.

Record commands, scope, result, candidate/version, duration when measured, and unresolved failures. Separate baseline debt from new failure. Estimated cost, elapsed tool time, model usage and unavailable metrics are different facts; do not invent throughput or savings.

## Current planning receipt

`pactile task verify-plan <task-id> --manifest <project-relative-json> (--adopt|--override) [--no-jev]` plans against the latest completed V2 candidate. The bounded manifest supplies impact and available check metadata, not executable commands or authoritative CI inventory. The command writes a candidate-bound planning receipt only: it does not run checks, start a Run, record Review or Close.

Deterministic planning retains required policy checks. Configured Jev can advise on optional checks under the project egress policy and recorded adoption/override; unavailable or refused advice falls back. Neither Jev nor a planning receipt grants permission, manufactures evidence or supplies the independent final verdict. Replan when the bound candidate changes.

## Review and Close

Implementation verification and independent Review are separate results. A reviewer checks requirements, code quality and material risks on the exact candidate, reports blockers and does not fix it. Reviewer identity must differ from the Run executor and approver. Preserve role capabilities while enforcing the actual authorized action boundary; a prompt or worktree does not prove read-only/OS protection. See [the role and dispatch contract](../modules/worker-orchestration/contract.md).

The Kernel closes only with the latest eligible completed Run, matching current candidate, latest independent passing Review without blockers, every AC's evidence, successful hard dependencies and the defined delivery-level evidence. Normal process exit, check count, old PASS, a retrieval pack or a human-readable summary is insufficient.

## Legacy boundary

V1 `start-execution`, gate profiles and directory archive apply only when the unified reader identifies that legacy schema. Do not upgrade a V2 Task into Full/Parent because risk rises; adjust the authorized design, checks or independent Task scope through supported operations.
